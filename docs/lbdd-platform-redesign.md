## 2. 用户旅程与断点(一个真实 LBDD 会话长什么样)

```
已知一个活性配体
  → 找相似物(1D 指纹粗筛 → 2D 子结构 → 3D shape/color → 药效团)
  → 命中清单做甄别(drug-likeness/警示/骨架分类/多准则排序)
  → 挑出候选,看 SAR(RGD 拆解/骨架聚类/共性与差异)
  → 定优先级,导出清单(带完整溯源)给下一环节(订购/合成/docking)
```

现有工作台的断点:

| # | 断点 | 现状 |
|---|---|---|
| B1 | **命中不流动**:每种检索的结果表各自为政,选中的分子只能"回载单视图",无法把命中集带入下一阶段(如对命中集整体做 RGD/骨架聚类) | 表间无管道 |
| B2 | **无甄别层**:检索结果没有收藏/排除/备注,没有跨检索轮次的"工作集"概念 | 一次性表格 |
| B3 | **无项目持久化**:刷新只剩搜索库;批量结果、检索轮次、甄别决策全部丢失 | localStorage 只存库 |
| B4 | **检索模式割裂**:1D→2D→3D 递进检索是 LBDD 的自然节奏,现在要手动切模式下钻 | 模式互斥 |
| B5 | **无迭代捷径**:"用这个命中做新查询再搜一轮"(lead hopping)要点四次 | 有 Use current 但不聚焦 |
| B6 | **表能力不统一**:Batch 有三态排序+五档过滤,Search 结果没有 | 两套表 |

## 3. 设计原则

1. **离线优先是身份**:专有化合物永不离机——这是对云端平台
   (LiveDesign/Design Hub/CDD)的差异化,不追服务器功能
2. **工作流连续性 > 功能堆叠**:分子/命中集在阶段间流动,而不是
   在标签页间搬运
3. **一张表统治**:所有结果 = 同一张命中表(列可配),排序过滤
   收藏贯穿
4. **零学习成本下限**:新手路径不比现在长;高级工作流渐进披露
5. **不破坏现有**:Single/Batch/Search 三标签骨架保留为新 IA 的
   三个视图入口,不推倒重来

## 4. 信息架构提案

```
┌─ 项目─────────────────────────────────────────────┐
│ (自动本地保存;可导出/导入 .webmm.json;多项目切换)    │
│                                                    │
│  左栏:化合物与查询          中央:命中表(统一)      │
│  ├ 库(可多个,现有概念)      列:结构缩略│名称│MW│    │
│  ├ 查询历史(每轮检索)          QED│PAINS│T/Combo│   │
│  └ 工作集(★收藏/✕排除)        Conf│来源检索│…可配   │
│                              行:点击→右侧检查器     │
│  右侧:检查器(详情)          工具条:                │
│  ├ 2D 结构+警示高亮           进入SAR│作新查询│      │
│  ├ 3D(特征球/电荷/叠合)        导出CSV/SDF│批量3D   │
│  └ 性质面板+构象图表                                │
└────────────────────────────────────────────────────┘
```

- **项目** = 库 + 查询轮次 + 各轮命中 + 工作集 + 备注,单 JSON 可序列化
- **统一命中表**:把 Batch 的三态排序/五档过滤下放给所有结果表;
  每行带来源(哪轮检索/什么分数)
- **检查器** = 现有 Single 视图的能力收进右栏(2D/3D/性质/警示/构象)
- **递进检索**:一个"下钻"控件——指纹命中集 → 一键在其上跑子结构 →
  再 shape(查询与库不换,集合逐步收窄;B4/B5 由此解)
- **SAR 入口**:对当前命中表(而非全库)做 RGD/骨架聚类(B1 解)

## 5. 路线图(三阶段,每阶段独立可用)

### M1 — 统一命中表 + 工作集(地基,纯 app 层)
- 命中表组件统一(Batch 表能力下放所有结果;列可显隐)
- 行级 ★收藏/✕排除,工作集跨轮次持久(localStorage 起步)
- 每行来源标注(检索轮次/分数类型)
- 交付判据:三种检索的命中都能收藏、排序、过滤、导出,刷新不丢

### M2 — 项目 + 递进检索(平台性)
- 项目序列化(导出/导入 JSON,自动保存)
- 检索轮次历史 + "以此命中为查询再检索"(lead hopping 一步化)
- 命中集 → SAR(RGD/骨架聚类)管道
- 检查器右栏(现有 Single 能力迁入,Single 标签保留兼容)

### M3 — 类似物探索(独门,引擎已有 80%)
- **类似物枚举器**:选中命中 → RGD 定连接点 → 内置小片段库
  (烷基/杂环/卤代/极性替换 ~100 个)经反应 SMARTS 枚举 →
  ETKDG 构象 → shape+color 对原查询打分 → 新类似物命中表
  (Spark/BROOD 的浏览器内简化版,全离线)
- 多查询共识排序(若干轮检索的秩平均)
- 骨架跳跃建议( MCS 换骨架保持药效团距离)

## 6. 资产映射与缺口

| 新 IA 组件 | 复用 | 缺口 |
|---|---|---|
| 统一命中表 | Batch 表引擎 | 抽组件+列配置+行状态 |
| 工作集 | 无 | 新(数据层小) |
| 项目持久化 | 库 localStorage 模式 | 序列化 schema + 导入导出 |
| 递进检索 | 全部检索引擎 | "在集合上检索"的入口与语义 |
| 检查器 | Single 全套 | 布局迁入,能力不动 |
| SAR 管道 | RGD/骨架/MCS | 以命中集为输入(现以全库) |
| 类似物枚举 | 反应 SMARTS/ETKDG/shape | 片段库数据+枚举编排(全新) |

引擎层零改动(M1/M2 纯 app;M3 也基本纯 app,必要时加批量接口)。

## 7. 待决策分叉点

1. **改造 vs 并行**:M1/M2 改造现有 Workbench,还是新起 `/platform`
   页面并行孵化、成熟后替换?(倾向:改造,三标签骨架保留)
2. **检索递进的形态**:下钻控件(收窄同一表)vs 显式管道视图
   (每轮一列,可回看)?(倾向:先做下钻,简单直接)
3. **M3 类似物片段库**规模与来源:内置 ~100 精选(可控)vs 可导入
   用户片段库(灵活)?(倾向:内置起步+SMILES 导入)
4. **项目文件格式**:纯 JSON(人可读,大库会胖)vs JSON+二进制指纹
   分离?(倾向:JSON 存输入,指纹恢复时重算——沿用现有库持久化
   的"存输入不存指纹"先例)
